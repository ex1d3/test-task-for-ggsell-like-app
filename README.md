## Как воспроизводить проблемы с провайдерами

Провайдеры настраиваются через переменные окружения в `docker-compose.yml` (контейнеры `provider-a` и `provider-b`):

- UPD: `DOUBLE_ISSUE_RATE` - вероятности выдачи уже выданого ключа
- `FAILURE_RATE` - вероятность ответа ошибкой
- `TIMEOUT_RATE` - вероятность таймаута
- `TIMEOUT` - длительность таймаута

Чтобы воспроизвести сценарии, меняйте эти значения и перезапускайте контейнеры провайдеров (`docker compose up -d provider-a provider-b`).

## Ключевые решения

- Идемпотентность вебхуков: event_id уникален в БД, повтор того же события не меняет состояние.
- Защита от гонок по статусам заказа: обновления статуса делаются "compare-and-swap" (обновляем только если текущий статус ожидаемый), чтобы параллельные обработки не запускали выдачу повторно.
- UPD: Автовыдача в фоне: отдельный таймер/воркер периодически забирает запланированные попытки доставки (delivery_attempts) и выполняет выдачу. Есть только три попытки на выдачу всех товаров, если после третьей попытки остались не выданые товары - по ним проходит возврат и заказ метится как частично завершенный. 
- Ретраи и бэкофф: при timeout создаётся следующая попытка с увеличивающейся задержкой; при 500 status code переключаем провайдера A/B.
- Ловушка таймаута: таймаут у провайдера трактуется как "мог выдать код"; повтор идёт с тем же request_id, а провайдер по request_id обязан вернуть тот же код (идемпотентность выдачи).
- UPD: повторная выдача: если по request_id не найдено существующей выдачи - с некоторыми шансом (который корректируется DOUBLE_ISSUE_RATE в env провайдера) выдается уже использованный ключ.
Само приложение разрешает такие ситуации через UNIQUE индекс в таблице order_items на поле code, что бы один и тот же код не использовался дважды.
